Homework 1 — Private key to public key on a toy curve

Aim and setup

This experiment demonstrates the idea behind elliptic-curve scalar multiplication. It uses the small finite field and curve

[ E: y^2 \equiv x^3 + 7 \pmod{17}, \qquad G=(1,5), \qquad k=6. ]

The point is valid because (5^2=25\equiv 8\pmod{17}), and (1^3+7=8). The public point is defined as (Q=kG), meaning that the base point is added to itself six times using elliptic-curve point addition.

Point addition

For two distinct points (P=(x_1,y_1)) and (R=(x_2,y_2)), the slope is

[ \lambda \equiv (y_2-y_1)(x_2-x_1)^{-1}\pmod{17}. ]

For doubling a point (P), the slope is

[ \lambda \equiv (3x_1^2)(2y_1)^{-1}\pmod{17}. ]

In both cases,

[ x_3\equiv\lambda^2-x_1-x_2\pmod{17},\qquad y_3\equiv\lambda(x_1-x_3)-y_1\pmod{17}. ]

Here, division means multiplication by a modular inverse, not ordinary floating-point division. If two points have the same x-coordinate and opposite y-coordinates modulo 17, their sum is the point at infinity (\mathcal O), which acts as the group identity.

Verified result

Scalar Operation Result
1 (G) ((1,5))

5 (4G+G) ((12,16))
6 (5G+G) ((5,8))
7 (6G+G) ((2,7))
8 (7G+G) ((1,12))
9 (8G+G) (\mathcal O)

Therefore, for the assignment's example, the toy public key is (Q=6G=(5,8)). The base point has order 9 because (9G=\mathcal O), while none of (G,2G,\ldots,8G) is (\mathcal O). Consequently, this base point can produce only nine subgroup elements, including infinity. A tiny group like this can be searched exhaustively and is completely insecure.

The accompanying elliptic_curve_toy_demo.html file lets the user change k and choose other valid base points, inspect a multiplication trace, see the curve plotted, and animate repeated point addition.

Statistical exploration

For (G=(1,5)), examine the eight distinct finite nonzero multiples (G,2G,\ldots,8G) (excluding (\mathcal O)):

  • x-coordinates are (1,2,5,12,12,5,2,1). Each of x = 1, 2, 5, and 12 occurs twice in this subgroup sample.
  • y-coordinates are (5,10,9,1,16,8,7,12). Each occurs once in this sample.
  • Each coordinate is between 0 and 16, so it can be represented using only five bits. The observed bit counts depend on this particular small subgroup and are not a meaningful cryptographic security test.
  • There is an obvious algebraic symmetry: ((n-k)G=-kG) for subgroup order (n). The inverse of ((x,y)) is ((x,-y\bmod17)). Thus inverse pairs have the same x-coordinate and opposite y-coordinates modulo 17.
  • The mapping is deterministic. Scalars that differ by a multiple of 9 produce the same group point: ((k+9)G=kG). There is also no requirement that adjacent scalars produce unrelated coordinates: ((k+1)G=kG+G).

For a real elliptic-curve public-key system, the important security property is that calculating (Q=kG) is efficient while recovering k from Q is computationally infeasible for appropriately chosen parameters. This is the elliptic-curve discrete logarithm problem (ECDLP). With a uniformly chosen scalar in the valid range and a suitable large subgroup, the point is distributed over that subgroup; this does not mean its x- and y-coordinate bits must satisfy a hash function's avalanche test.

A cryptographic hash function has a different job: it maps arbitrary-length input to a fixed-size digest and should offer preimage resistance, second-preimage resistance, and collision resistance. The avalanche effect—small input changes causing large, apparently unpredictable digest changes—is a useful design goal/diagnostic associated with hashes, but it is not by itself a proof of security. Scalar multiplication is structured group arithmetic, not a hash function. The toy experiment is too small to establish any real cryptographic property.

Homework 2 — From a wallet mnemonic to an Ethereum address

Simplified wallet pipeline

For a common mnemonic-based Ethereum externally owned account (EOA), the high-level process is:

  1. Entropy → mnemonic (BIP-39): a wallet creates random entropy and encodes it as a sequence of words, adding a short checksum to the entropy before mapping chunks to a word list. The mnemonic is convenient to back up; it is not itself the final private key.
  2. Mnemonic → seed (BIP-39): the normalized mnemonic and optional passphrase are processed with PBKDF2-HMAC-SHA512, using 2,048 iterations, to produce a 512-bit seed. An optional passphrase changes the resulting seed; it is not a substitute for protecting the recovery phrase.
  3. Seed → master key and child keys (BIP-32): BIP-32 uses the seed to derive a master extended private key and chain code, from which it can deterministically derive a hierarchy of child keys. Derivation is repeatable for the same seed and path.
  4. Path selection (BIP-44): BIP-44 defines a conventional hierarchy: m / purpose' / coin_type' / account' / change / address_index. Ethereum commonly uses m/44'/60'/0'/0/0 for the first address, with coin type 60' assigned to Ethereum. The precise path can vary by wallet and account type.
  5. Private key → public key (secp256k1): the private scalar k is used to calculate the elliptic-curve point (Q=kG). Ethereum uses the secp256k1 curve with ECDSA signatures. The public key can be shared; the private key must remain secret.
  6. Public key → address (Keccak-256): take the 64-byte x-coordinate || y-coordinate form of the uncompressed public key (omit the leading 0x04 format byte), hash it with Ethereum's Keccak-256, and take the last 20 bytes of the 32-byte digest. Add the 0x prefix to display the 20-byte address as 40 hexadecimal characters.
  7. Address → checksummed display (EIP-55): hash the lowercase hexadecimal address text (without 0x) with Keccak-256 and use the corresponding hash nibbles to determine which letters a–f should be uppercase. This mixed-case encoding helps detect many typing errors. It does not encrypt an address or prove who owns it.

What each primitive contributes

Standard / primitive Main purpose Category What it does not do
BIP-39 Makes wallet backup human-readable and converts mnemonic plus optional passphrase to a seed Mnemonic format and seed derivation It does not derive every account's child key by itself
BIP-32 Builds a deterministic tree of extended keys and child keys from a seed Hierarchical key derivation It is not the elliptic curve or address hash
BIP-44 Specifies a conventional account/coin/change/address hierarchy and path structure Wallet organization / derivation path It is not a cryptographic primitive by itself
secp256k1 Relates private scalar and public point; supports ECDSA digital signatures Public-key cryptography It is not a hash function and does not make a weak private key safe
Keccak-256 Produces a 256-bit digest used to derive Ethereum addresses Cryptographic hashing It does not create a key pair or provide address checksumming by itself
EIP-55 Adds mixed-case error-detection information to hexadecimal address text Checksum encoding It is not encryption, authentication, or a complete defense against all errors

Key generation vs. key derivation: generation begins with fresh, cryptographically secure random entropy. Derivation deterministically computes repeatable keys from existing secret material and a path. A wallet commonly generates a mnemonic from entropy and later derives many child private keys from its BIP-39 seed using BIP-32/BIP-44.

Public-key cryptography vs. hashing vs. encoding: public-key cryptography creates a private/public key relationship and enables signatures. Hashing deterministically compresses input into a fixed-length digest. A checksum encoding uses a deterministic rule to make some accidental text errors detectable. Hexadecimal and the 0x prefix are representation/encoding choices; neither provides secrecy.

Why not use one algorithm for everything?

These steps solve different problems. BIP-39 makes backup material manageable for humans; BIP-32/BIP-44 organize repeatable account and address derivation; secp256k1 provides the private/public relationship and signature mechanism; Keccak-256 turns the public key into a compact address identifier; and EIP-55 helps people detect mistyped addresses. Reusing one algorithm for all those roles would not automatically provide the right interface or security properties for each job.

Statistical properties

  • BIP-39: word sequences are not arbitrary English sentences when produced correctly; they encode entropy plus a checksum. Mnemonic-word frequencies depend on the word list and entropy-to-index construction, so natural-language frequency expectations do not apply. The short checksum catches some mistakes but cannot correct them and does not replace secure entropy.
  • BIP-32/BIP-44: derivation is deterministic. The same seed and path produce the same child key. The index/path is structured input, not a source of independent random keys. Correctness and compatibility matter more than whether a short list of child-key numbers looks uniform.
  • secp256k1: valid private scalars are selected from a large integer range associated with the base point's subgroup order; public keys are points generated by scalar multiplication. Point coordinates have algebraic structure, and they should not be judged using the same avalanche criteria as hashes.
  • Keccak-256: a cryptographic hash is designed to produce fixed-length digests with strong diffusion and resistance to preimages and collisions. In short samples, output bits should look irregular, but an informal frequency check is not a proof of these properties.
  • EIP-55: capitalization follows a deterministic rule based on the hash of the lowercase address text. Letter-case patterns are therefore not random decoration; they encode error-detection information. EIP-55 catches many, but not every possible, address transcription error.

Do not infer security from histograms with tiny samples. For real wallets, the best practice is to use a reputable, reviewed wallet implementation with secure entropy and to keep the recovery phrase/private keys secret. Never paste a real recovery phrase or private key into a homework demo or website.

The prompt's date “SHA-2 / SHA-512 standardized in 2001” is best refined: SHA-2 was developed around that period, but NIST's FIPS 180-2 publication that specifies SHA-256, SHA-384 and SHA-512 is dated August 2002. RSA is often dated to 1977 for its development, while the public paper was published in 1978.

SHA-2 / SHA-512 vs. Keccak / SHA-3

SHA-2 and SHA-3 are distinct hash-function families with different internal designs. SHA-512 is a member of SHA-2. SHA-3 is the standardized family based on Keccak, the winner of NIST's SHA-3 competition. Ethereum uses Keccak-256, not the standardized SHA3-256 function: although they share the Keccak permutation/design ancestry and both output 256 bits, their padding/domain-separation convention differs. Consequently, calling a generic SHA3-256 implementation usually will not produce the Ethereum address hash expected by wallets.

Conclusion

A mnemonic is a backup representation, the seed is input to hierarchical key derivation, the derivation path chooses a specific account key, elliptic-curve cryptography generates the public key and supports signatures, Keccak-256 derives the address bytes, and EIP-55 adds readable error-detection information to the address string. Their roles complement each other but are not interchangeable.
